# Testing the Rust port

PHP is the specification. A ported component is right when it answers like
PHP: the same JSON for a Conduit method, the same objects, visibility and
actions for a page. Every test below checks that against PHP in one way or
another, from the cheapest to the closest to production.

## Layers

| Layer | What it proves | Where | Runs |
|---|---|---|---|
| 1. Unit tests | Pure logic: parsers, codecs, policy rules, PHP value semantics | `#[cfg(test)]` modules | `cargo test`, CI |
| 2. Ported PHP tests | The behaviour PHP's `__tests__` already pin down | `crates/*/tests` (e.g. the Remarkup corpus of `PhutilRemarkupEngineTestCase`) | `cargo test`, CI |
| 3. Database tests | Queries, edges, fixtures and the schema contract on a real MySQL 5.7 | `crates/*/tests` with `phab_db::testing::TestDatabase` | `cargo test` with `PHAB_TEST_MYSQL_URL`, CI |
| 4. PHP oracles | Rust output equals what PHP's own code produces for the same input | `tests/oracle/*.php` and `tests/data/*.php`, their output checked in | Regenerated by hand, the checked-in output in CI |
| 5. HTTP tests | Routes, authentication, fallbacks (`421`) and shadow mode, in process | `bins/phab-server/tests`, `crates/phab-web/tests` | `cargo test`, CI |
| 6. nginx routing | Which stack answers each route, fallback to PHP, Rust missing | `scripts/test-nginx-routing.sh` | CI |
| 7. Replay | The same calls give the same answers on both stacks | `rust/parity/*.json`, `phab-replay` | By hand, on the dev stack |
| 8. Shadow | The same, on real traffic, without users seeing the Rust answer | `PHAB_SHADOW_METHODS`, `GET /status` | Dev stack, then production |
| 9. Web flows | A user sees and can do the same things in both interfaces | Playwright (not written yet) | Dev stack |

### 1–3. Unit, ported and database tests

- Port the PHP test case along with the code, and keep its fixtures as
  they are, so the two can be compared line by line.
- Database tests build their own database from `quickstart.sql` plus the
  newer autopatches, so they always see the current schema. Without
  `PHAB_TEST_MYSQL_URL` they are skipped; `PHAB_TEST_REQUIRE_MYSQL=1` (set in
  CI) turns the skip into a failure.
- Every table and column the Rust code reads is listed in
  `crates/phab-db/src/schema.rs`, and a test checks the list against the
  schema. A PHP migration that breaks Rust fails there first.
- Codecs that read data PHP wrote are property tested (`proptest`, see the
  `serialize()` codec in `phab-db`).

### 4. PHP oracles

When PHP's tests don't cover a behaviour, run PHP itself and check its
output in as the expected value:

- `crates/phab-remarkup/tests/oracle/generate.php`: random documents,
  compared when `PHAB_REMARKUP_ORACLE` points to the generated file (30k
  documents matched).
- `crates/apps/differential/tests/oracle/titles.php`: feed titles of
  Differential transactions (`titles.expected`).
- `crates/phab-diff/tests/data/pipeline.php`: hunk parsing and realignment
  (`pipeline_expected.json`).

Each script says in its header how to regenerate the output. Regenerate it
when the PHP side changes, and say so in the commit.

### 5–6. HTTP and nginx tests

- Every route needs a test for the anonymous viewer, a viewer who can't see
  the object, and each case that must fall back to PHP (`421` with
  `X-Phab-Fallback`). Falling back is always correct; answering wrongly is
  not, so when in doubt the code falls back and the test says why.
- Shadow mode is tested against a fake PHP server: the client gets PHP's
  answer, and differences are counted, not returned.

### 7–8. Replay and shadow

A Conduit method goes through the three steps of the README: shadow,
replay, serve. To serve a method, its scenario file in `rust/parity/` must
replay without differences on the seeded dev stack
(`scripts/seed-dev-stack.sh`), and its shadow counters in production must
show no differences over a period that covers its real callers (moz-phab,
Lando, the bots). The fallback rate in `/status` tells how much of the
method is really ported.

### 9. Web flows

The Rust pages don't reproduce PHP's HTML, so they are compared on data,
not markup: for the same viewer and object, both interfaces must show the
same objects, hide the same ones and offer the same actions. Playwright
flows on the seeded dev stack, logged in as each seeded user, cover:

- the review queue and its buckets;
- a revision in every review state, a private one, a secure one and a
  stack;
- the review flow (comment, inline, accept), where the transactions, mail
  and feed rows it creates must match the same flow in the old interface.

## Rules for each ported component

1. Unit and ported PHP tests, and an oracle where PHP's tests are thin.
2. Policy: a test for every way the object can be hidden (policy, space,
   parent, membership), and that a hidden object never leaks through a
   handle, a title, a count or a link.
3. Fallbacks: every case not ported answers `421` and has a test.
4. Conduit methods: a `rust/parity/` scenario file, then shadow mode.
5. Pages: an HTTP test per viewer kind, then a Playwright flow.
6. `cargo +nightly fmt --check`, Clippy with `-D warnings` and the tests
   pass, with MySQL.

## Not done yet

- No Playwright flows yet; pages are checked by HTTP tests and by hand.
- `phab-replay` has not been run on seeded data, and shadow mode has seen
  only empty data.
- The oracles run by hand, so CI only checks the output they produced.
  Running them in CI needs a job with PHP and libphutil.
- No golden corpus from production comments and diffs yet.
